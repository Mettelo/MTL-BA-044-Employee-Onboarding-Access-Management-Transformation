# Existing starter, access and leaver forms/messages
**Mettelo BA-044 · Stage 3 · Fictional source copies**

## HR starter form
Employee local ID: ____ / team: ____ / manager: ____  
Start date: ____ / office or remote: ____ / equipment: standard or other  
Delivery route: ____ / HR approval attached: yes or no  

The form has one start-date field, no change version/acknowledgement and no application-owner reference. It is not the future data model. Do not complete it with real addresses or personal information.

## Access request sheet
Employee ID: ____ / application: ____ / access description: ____  
Business reason: ____ / manager email: ____ / approve or reject: ____  
IT completion tick: ____  
Free-text instruction: “Same as colleague if appropriate.”

There is no controlled privileged-access status, expiry, application-owner evidence, review or user-verification field. The source is not an approved role/access matrix or permission catalogue.

## Existing service checklist
Contract approved — HR tick. Laptop ready — dispatch reference. Account created — directory event. Desk/pass — Facilities tick. Welcome email — manager sent.
No field requires actual delivery, effective-date acknowledgement or all-required-application verification. The checklist describes existing usage; it is not the participant's proposed future process.

## Starter completion message
“Your setup is complete. Please contact your manager if anything is missing.”
The source trigger is ticket closure. The message does not distinguish dispatched, delivered, login-ready or pending application work. The pack does not establish every actual message sent.

## Leaver note
Employee ID: ____ / leaving date: ____ / disable at 17:00  
Directory done: ____ / pass done: ____ / other: ____  
The note has no effective-time override, independent application list or explicit unverified status. L0082 provides a relevant noon-departure source example, but no complete revocation design is supplied.

## Use by the BA
Investigate missing meaning, hand-offs, ownership, exception handling and information access. Redesign, field/rule proposals, requirements, user stories, test expectations and acceptance criteria are participant work. Keep source forms separate from future artefacts and do not assume a simpler form eliminates appropriate control decisions.
